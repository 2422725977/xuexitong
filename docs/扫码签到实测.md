# 扫码签到实测：客户端门禁与二维码提交契约

> 实测时间 2026-11-15（真实账号 + 桌面浏览器会话，非模拟器）
> 目标课程：计算机二级（courseId `269282723` / clazzId `159926750`，puid 记为 `<PUID>`）

## 1. 关键发现：学生活动列表有"客户端门禁"

请求 `GET https://mobilelearn.chaoxing.com/ppt/activeAPI/taskactivelist?courseId=<C>&classId=<K>&uid=<PUID>`（这个 URL 模板来自反编译 `Lhc/a;->Z()`）：

| 请求特征 | 结果 |
|---|---|
| Chrome 桌面 UA | `200 {"status":0,"activeList":[],"groupList":[],"count":0,"result":0,"errorMsg":"请用学习通客户端打开活动列表"}` |
| `okhttp/4.12.0` UA（App 原生层 UA） | 同上（被拒） |
| App WebView UA + `X-Requested-With: com.chaoxing.mobile` + `Referer: https://mobilelearn.chaoxing.com/` | **200 正常返回**（`status:1`，带 `activeList` 与 `groupList` 计数） |

App WebView UA 模板（来自载荷字符串，versionCode 10946）：

```
Mozilla/5.0 (Linux; U; Android 13) AppleWebKit/533.1 (KHTML, like Gecko) Version/4.0 ChaoXingStudy_10946Safari
```

**门禁只看 UA 串里有没有 `ChaoXingStudy_<versionCode>`**（+ 常规 H5 头），不是签名、不是 token、不是设备指纹。
`基础参数（uid / cpi / appType=15`）加不加都一样被拒，说明判定发生在前置过滤器。

## 3. 提交契约（通道 C：`pptSign/stuSignajax`）

学生端 preSign 页面（`newsign/preSign?...&isTeacherViewOpen=0`，29 KB）里的 JS 拼装（`navOpen()`）：

```
/pptSign/stuSignajax?enc=<enc>&name=<name>&activeId=<aid>&uid=<puid>&clientip=&location=
  &latitude=-1&longitude=-1&fid=<fid>&appType=15&deviceCode=&vpProbability=&vpStrategy=
```

- 成功判定：响应纯文本 `success` / `success2`（另有 `checkFace_*`、`validate_*` 前缀表示要人脸/验证码，本活动无）
- `#activeId`、`#fid`、`#uid` 是页面隐藏域（服务端渲染），`name` 由 App 通过 jsBridge `getCurrentApplyUserInfo` 注入（纯浏览器会话里为 `""`，服务端按会话 uid 认定，不影响判定）

## 4. enc 从哪里来：只在二维码里

二维码内容 = 一个 `widget/sign/e` 链接：

```
https://mobilelearn.chaoxing.com/widget/sign/e?id=<aid>&c=<签到码>&enc=<enc>&DB_STRATEGY=PRIMARY_KEY&STRATEGY_PARA=id
```

链路：扫到这个链接后 → 页面 302 到
`newsign/preSign?...&rcode=SIGNIN%3Aaid%3D<aid>%26source%3D15%26Code%3D<c>%26enc%3D<enc>` →
preSign 的 JS `sacn_callback()` 把 `rcode` 拆开取出 `enc` → 拼出上面的 `stuSignajax` URL 提交。

**`enc` 是服务端在教师侧生成、随二维码下发的绑定值，客户端算不出来**；`ifRefreshEwm=1` 时 `c`（=signCode）每 ~10 秒轮换，所以必须实时取到那一帧二维码。

→ 服务端不校验 name/fid/clientip，也不因"非 App 环境"拒绝提交；**唯一硬条件是有效的 enc**。

## 6. 实测命令（三种输入方式，全部已验证到"提交并被服务端处理"）

```bash

python3 scripts/qr_relay.py --source screen --interval 0.6 \
  --submit --cookie-file ck.txt --uid <PUID> --name "" --fid 0 --stop-on-success --verbose

# B. 直接把二维码内容贴进来（`widget/sign/e?...` 链接或 `SIGNIN:aid=…&enc=…` 串）

  --cookie-file ck.txt --uid <PUID>

# C. 目录投喂 / 手机同步盘：外部工具往 out/qr_in 丢截图
python3 scripts/qr_relay.py --source loop-dir --dir out/qr_in --interval 1 \
  --submit --cookie-file ck.txt --uid <PUID>
```

本轮顺带修的两个坑：

1. `qr_relay.py` 的解码器加了多尺度（1×/2×/3×/4×）+ 反色 + 原始/灰度双通道；此前 cv2 生成的小尺寸二维码（41×41 无白边）解不出来，现在能解。
2. `--source loop-dir` 原先"先改名成 .used 再解码"，解不出就把图吃掉；改成"解码后再打标记"，并跳过 `.used`。

## 8. 结论

- 从"能列出活动 → 拿到 aid/signCode/类型"这一段，纯 HTTP + 桌面会话 + App WebView UA 就够，**不需要模拟器、不需要 frida**。
- 最后一步的 `enc` 只能来自二维码本身：教师屏幕上那一帧，或者把二维码图片/链接喂给中继。
- 因此远程扫码的可行形态是：**看屏中继（本机屏/被控端屏/同步相册）→ 解码 → 带自己的会话提交**，dn 秒级，动态刷新也能跟上。

## 9. 过期二维码与"绕过二维码"的实测边界（2026-11-15 17:00）

社区所有项目的共同前提：**enc 必须由人提供**（粘贴二维码链接 / 传入 enc 参数），没有任何一家能生成或续期 enc。
- cxOrz/chaoxing-signin `apps/server/src/functions/qrcode.ts:4`：`QRCodeSign({enc,name,fid,activeId,lat,lon,address,altitude})` → enc 是入参。
- HEDBS/chaoxing-sign `chaoxing_sign.py:151`：`sign_qrcode(act, enc, lat, lon, address, altitude="100")` → enc 是入参。

→ 因此"过期二维码"这件事发生在**拿到 enc 之前**，社区代码在结构上无法解决；能采用的只是它们提交参数的拼法（如定位类需要的 `location` JSON）。

### 9.1 PC 通道不给二维码签到留口子（实测）

| 探测 | 结果 |
|---|---|
| GET /widget/sign/pcStuSignController/preSign?activeId=4000180737792&signCode=211869 | 200 / 4,787 B，正文**"此签到需要手机扫码 / 请使用手机App 在本课程任务下签到"**，无签到按钮 |
| GET /widget/sign/pcStuSignController/checkSignCode?activeId=&signCode=211869 | 200 `{"result":1,"msg":"验证成功","data":null,"errorMsg":null}`（只校验码，不落签到） |
| pcStuSignController/{stuSign,sign,doSign,stuSignajax}、newsign/stuSign、pptSign/stuSign、widget/sign/stuSign | 全 500（不存在） |

结论：activeType=2（二维码签到）**没有免扫码的服务端提交入口**；PC 输码只对签到码类（otherId=5）有效。

### 9.2 生成接口够不到（实测）

23 个候选生成端点全部 500：/widget/sign/{getEwm,getSignEwm,ewm,qrcode,signEwm,e/get}、/newsign/{getEwm,getSignEwm,ewm,signEwm,qrcode,refreshEwm}、/pptSign/{getEwm,ewm,signEwm,signCode}、/widget/sign/pcTeaSignController/{getEwm,preSign,teaSign}、/widget/sign/teaSignController/preSign、/widget/sign/api/{getEwm,signEwm,ewm}。
载荷 out/dumped_strings.txt 中无任何 ewm 生成串（只有 zxing 本地解码库）。→ 生成逻辑在教师端 H5，学生会话够不到；**拿到教师 cookie 后可从其页面 JS 挖出接口**。

### 9.3 "过期"的真实语义（关键假设，待验证）

GET /newsign/signDetail?activePrimaryId=4000180737792&type=1 持续返回 **isOver=1**（17:00:22–17:00:32 六次采样恒定），而活动本身 status=1、剩余 36h59m、signCode=211869 自 16:38 起 22 分钟未变。
- 客户端 JS：`if(res.isOver==1){ showTip("二维码已过期"); return; }` → isOver 描述**这枚二维码（ewm 展示会话）**，不是活动。
- signCode 只在教师端二维码页打开时轮换（16:34 截图 c=104439 → 之后变 211869 后冻结）→ 教师页关闭即 ewm 置 over，随后任何 enc 都被拒为"签到失败，请重新扫描。"。

判定实验（一步可定）：教师端二维码页保持前台 → 若 isOver 翻回 0，用 16:34 那张旧图的 enc 提交：
- 成功 ⇒ enc 是活动级恒定值，**"过期"只是展示会话被关闭**（教师页持续开着，任意旧截图永久可用）
- 失败 ⇒ enc 与帧绑定，必须新鲜帧（3 s 刷新下 0.5 s 轮询中继可跟）

工具：`python3 scripts/ewm_watch.py --aid 4000180737792 --cookie-file ck.txt --enc <enc> --submit --uid 493228247`

### 9.4 社区方案逐字复现 + 服务端错误文案分类（2026-11-15 17:3x）

**逐字复现 cxOrz 的请求**（`apps/server/src/functions/qrcode.ts:7` 的 URL 模板，含 location JSON 与 altitude，整串 encodeURI 后发送）：
```
GET /pptSign/stuSignajax?enc=<旧enc>&name=&activeId=4000180737792&uid=493228247&clientip=&location={"result":"1","address":"","latitude":0,"longitude":0,"altitude":0}&latitude=-1&longitude=-1&fid=0&appType=15
→ HTTP 200  签到失败，请重新扫描。
```
同样结果：POST 表单提交、先用 `widget/sign/e?id&c=<当前c>&enc=<旧enc>` 扫一次再提交、先 `/newsign/signDetail?…&msg=SIGNIN:…` 再提交。`name` 取空/"测试"/"x"、`fid` 取 0/12 亦无变化。→ **差别不在参数或流程**。

**服务端错误文案是分类的（关键）**：
| 提交目标 | 响应 |
|---|---|
| 二维码指向的 clone `4000180737792`（status=1） | `签到失败，请重新扫描。` |
| **父活动** `4000180737791`（status=0，isClone=0） | `此次签到未开始` |
| 伪造 enc `test123` | `签到失败，请重新扫描。` |
→ 我们的文案 = **enc 验不过**（过期或伪造），不是活动状态或参数问题。

**活动结构**：taskactivelist 当前认可 3 条 —— id=-1(作业/考试 type19)、`4000180737792`(type2,status=1,可签)、`4000180737215`(type2,status=2,已结束)。clone `4000180737792`：parentId=4000180737791、signCode=211869（6 位数字，与旧二维码里的 c=104439 同型）；父活动 signCode=XZDE6S、status=0。两侧 submit 均失败（clone → 请重新扫描；父 → 未开始）。

**博客结论的边界**：[log.1k.ink/p/chaoxing](https://log.1k.ink/p/chaoxing) 的原始证据只是"10 秒刷新前后两张二维码 id/enc 相同、仅 c 不同"→ 仅证明 **enc 在很短时间窗内不变**；原文"任意一张该签到活动中的二维码图片解码出 enc 就能签到"是**外推**，作者未测过隔较久再提交。我们实测：截图后约 56 分钟提交 → 被拒。→ enc 存在**时间桶**：10 秒内不变，跨桶即失效。

**唯一未被排除的变量 = 帧新鲜度**（3 s 刷新下 0.5 s 轮询中继可跟），以及"教师 cookie 自造二维码"（彻底去掉人工延迟）。

## 10. 模拟器路线实测：App 在模拟器里能不能跑、能不能替代扫码（2026-11-15 17:4x）

目标：回应"用逆向数据 + 安卓模拟器走 App 自己的扫码链路"。三条判据：① App 在模拟器里能不能跑起来；② 跑起来后是否比 HTTP 直连多出能力；③ 全新安装是否有差别。

### 10.1 结论先给

- App **在模拟器里跑不起来**：启动约 3 秒后**原生自杀**（SIGSEGV 跳向近乎 0 的地址），API 29 与 API 30、去 root 与不去 root、新旧安装**全部一样**。
- 就算跑起来也**不解决"过期二维码"**：App 签到页初始化时 enc 为空（只能从扫码回调拿），并且它自己会先校验二维码新鲜度，过期码连提交请求都不会发。
- 真正能落地的两条：**新鲜帧**（看屏/截图即签，已就绪）与**教师 cookie**（自己取当前二维码内容 + enc，不怕过期）。

### 10.2 实测证据（崩溃）

命令（两个镜像都做过，全新 AVD + 全新安装）：

```bash
adb -s emulator-5556 install -r -t samples/学习通.apk      # Success
adb -s emulator-5556 shell 'am start -W -n com.chaoxing.mobile/.activity.SplashActivity'
```

### 10.4 就算 App 能跑，也没有新能力（App 自己的 JS 为证）

学生签到页原文（`out/preSign_4000180737792.html`，29,356 B）：

```js
var aidInEwm = ""; var enc = "";                       // 初始为空：学生端无法自造/续期 enc
jsBridge.bind('CLIENT_BARCODE_SCANNER', sacn_callback) // enc 只能来自扫码回调
enc = getUrlParam(msg, "enc")
// 新鲜度闸门（在发提交请求之前）
if (res.isOver && res.isOver == 1) { showTip("二维码已过期"); return; }
if (msg == res.signCode) { setTimeout("navOpen()", 500); } else { showTip("二维码不正确"); }
```

→ 过期码在 App 里**先被客户端拒绝**，然后才是服务端拒绝（服务端实测：`签到失败，请重新扫描。`）。模拟器把同一枚过期 enc 送给同一台服务端，结果不会变。

### 10.5 三条可执行路线（按性价比）

1. **新鲜帧（已就绪、可常驻）**：Mac 屏幕有二维码时用 `--source screen`；手机拍完截图 AirDrop 到 Mac 时用 `--source loop-dir --dir ~/Downloads`。0.14 s 解码、0.8 s 轮询、sha1 去重、RiskGuard 熔断。
2. **教师 cookie（一次投入，永久解决"过期"）**：`scripts/tch_qr_probe.py` 用教师登录态反复拉教师端签到页，抽出当前 `widget/sign/e?id=…&c=…&enc=…` 与候选 enc/signCode（并跨轮比对是否变化），拿到后直接喂 `qr_sign_remote.py` 提交 → 不需要真人扫码，可全自动；签到由谁发起都是你（教师）决定，天然免去人工延迟。
3. **真机/云真机**：真机不触发这套自检（用户的手机能正常用），但扫到的仍是同一枚二维码 → 依旧要新鲜帧；价值仅在于"复现 App 行为"，不增加签到能力。
