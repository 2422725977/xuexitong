## 1. 解壳：从运行内存里把真实 dex 拿出来

### 1.1 为什么静态解壳不行
- `classes.dex` 98,377,912 B，真实内容只到 ~24,728 B：17 个类（12 个 ARouter 路由 + 5 个 `com.secneo.apkwrapper.*`），其后 ~98 MB 是密文载荷。
- 2,570 个 zlib 头候选 inflate 成功 0；区域头 ×256 单字节 XOR 无 `dex\n035`；末尾 8 MB 是高熵随机 → 静态无解。
- `lib/arm64-v8a/libDexHelper.so`（1,070,509 B）含 14 个 VMP 标记（en_fun / g_func_map / dexflag / multidex_entry / JNI_OnLoad…）+ 624 条加密名表，节头被抹。
- 运行时确认：`.cache/oat/arm64` 与 `code_cache` **始终为空**，dex 只在内存，不落盘。

### 1.2 关键观察
- 壳在 ~3.4 s 时用一个**伪造上下文**（sp=0 / lr=0 / pc=0x3d8）主动 SIGSEGV 自杀，线程名 masquerade 成进程名 → 这是**风控检出模拟器/frida 后的自杀**，不是崩溃。
- 但**自杀前应用已经正常工作**：2.5 s 时已创建 chaoxing.db / ssreader_db_sqlite.sqlite 等十多个库、写业务日志、映射 base.apk → **真实 dex 此刻已在内存中且已解密**。
- 只要在 3.4 s 窗口内 `SIGSTOP` 冻结进程，之后用 root 读 `/proc/<pid>/mem`，进程随后死掉也无所谓。

### 1.3 做法（可复现）
1. 启动 AVD（API29 default arm64-v8a，`-writable-system`），`adb root` 可用；真机同理需 root。
2. 拉起应用，等 ~2.5 s，`kill -STOP <pid>`。
3. 解析 `/proc/<pid>/maps`，对每个 **rw 且 ≥1 MB** 的区域用 `dd if=/proc/<pid>/mem bs=4096 skip=PAGE count=PAGES` 落盘。
   - ⚠️ 坑 1：toybox sh 的 `$(( ))` 是 **32 位**，`$((0x7e90752000))` 溢出成负数 → dd 报 `-456878 < 0`，dump 全 0 字节。必须用「字符串切分算页号」的 64 位安全算法（见 `chaoxing/scripts/snap3.sh` 的 `pg()`）。
   - ⚠️ 坑 2：toybox dd 不支持 `iflag=skip_bytes,count_bytes`。
4. 把 dump 拉回本机，按 dex magic `dex\n035\0` + 头部自校验（`header_size==0x70`、`endian_tag==0x12345678`、`string_ids_off==0x70`、`map_off < file_size`）定位，再用 **adler32 校验和 + SHA-1** 判定真假（`chaoxing/scripts/extract_dex.py`）。
5. 校验通过的 dex 打包成一个 zip（`classes.dex, classes2.dex …`）交给 droidasc 反编译。

## 3. 扫码签到完整协议（核心链路）

### 3.1 时序
1. `SignInfoActivity.onCreate` → 取 `puid = AccountManager.C().D().getPuid()` → `o5()` 用 `ActivityResultLauncher` 启动内置扫码（zxing）。
2. 扫码结果 `SignResult.scans[0].content` → `SignInfoActivity$b.a()` → `j5(content)`。
3. `j5` 校验 puid 非空 → `m5(content, puid)`。
4. `m5`：`JSONObject(content)` 取 **`time`**、**`signId`**；
   `phoneId = an.b.d()`；
   `enc = com.fanzhou.util.j.d(signId + "-" + puid + "-" + time + "-" + phoneId)`（即 **MD5 小写 hex**）；
   拼 URL → Volley `StringRequest` GET 提交。
5. 响应 JSON → `SignInfoActivity$c` Handler：
   `{"statusCode":300,"status":true/false,"msg":"…","stuName":"…","data":{"userName","courseName","className","addTime":{"time":<ms>}}}`
   成功 → 显示「恭喜你签到成功！」(`R.string`)，失败 → 按 statusCode 显示错误文案。

### 3.2 请求
```http
GET https://fanyappfy.chaoxing.com/usersign/addsign?signId={signId}&userId={puid}&time={time}&phoneId={phoneId}&enc={enc}&ctype=stusign
Cookie: <学习通登录态 cookie（_uid/_d/uf/vc3…）>
User-Agent: <学习通 App UA>
```
- 基址常量：`wm.a.a = gc.b.j + "usersign/addsign?"`；`gc.b.j` 默认 `https://fanyappfy.chaoxing.com/`（可被服务端下发配置覆盖，`gc.b.d(String)`）。
- `ctype=stusign`（学生签到）；字符串池中只出现这一种 ctype。

### 3.3 enc 算法（com.fanzhou.util.j）
```java
public static String d(String s) {           // 标准 MD5 → 小写 hex（补前导 0）
    MessageDigest md = MessageDigest.getInstance("MD5");
    md.update(s.getBytes());                  // UTF-8 默认
    ...  // 逐字节 Integer.toHexString(b<0?b+256:b)，<16 补 "0"
}
```
即：
```python
enc = hashlib.md5(f"{signId}-{userId}-{time}-{phoneId}".encode()).hexdigest()
```
同文件还有：`j.b()` 标准 MD5、`j.c()` 取 MD5 的 [8:24] 16 位、`j.e()` GBK 编码 MD5——签到链路只用 `j.d()`。

### 3.4 phoneId（com.chaoxing 的 an.b）
- `an.b.d()` 返回 SharedPreferences `appProfile` / *key=uniqueId* 里的字符串；
- 首次为空则 `UUID.randomUUID().toString().replaceAll("-","")`（32 位无横线hex）并写回；
- `an.b.e()`/`f()` 另有一个 int 版唯一 ID（`SP_KEY_UNIQUE_INTEGER_ID`，UUID hashCode & 0x7fffffff）。
- ⇒ **任意固定 32 位 hex 即可**，服务端不做设备绑定校验（客户端也只是自增/持久化）。

### 3.5 服务端错误码（SignInfoActivity.k5）

|---|---|

| 301 | 签到失败（数据库插入失败） |

## 5. 客户端校验面

- **定位**：`LocationUtils` 用**百度定位 SDK**（`com.baidu.location`），`bd09ll`、3 s 扫描、需 ACCESS_FINE/COARSE_LOCATION；位置签到把经纬度交服务端判定，客户端不做距离校验。
- **扫码**：内置 `com.chaoxing.android.scan`（zxing）；二维码内容就是 `{"time":..,"signId":..}`。
- **唯一性**：phoneId/UUID（见 3.4），弱绑定。
- **风控（非签到协议本身）**：梆梆 everisk（`RiskStub.dex` 537 类 `com.coralline.sea.*`）负责环境检测（模拟器/frida/多开），检测失败会杀进程；它与签到接口的 enc 无关。
- ⇒ **复现签到不需要逆向壳，只需要登录态 cookie + signId/time + 该 MD5**。

## 6. 复现客户端

见 `chaoxing/scripts/sign_client.py`（占位符版本，直接可跑）。

```python
import hashlib, json, uuid, requests

BASE = "https://fanyappfy.chaoxing.com/usersign/addsign?"
COOKIE = "COOKIE_PLACEHOLDER"          # 从已登录客户端/抓包取
UID    = "PUID_PLACEHOLDER"            # AccountManager 的 puid，即 cookie 里的 _uid
PHONE_ID = uuid.uuid4().hex            # 32 位无横线，可固定复用

def sign(qr_content: str):
    try:
        d = json.loads(qr_content)     # 二维码内容形如 {"time":..., "signId":...}
        sign_id, ts = str(d["signId"]), str(d["time"])
    except Exception:
        # 兜底：二维码是 URL 查询串
        q = dict(p.split("=", 1) for p in qr_content.split("?")[-1].split("&") if "=" in p)
        sign_id, ts = q["signId"], q["time"]
    enc = hashlib.md5(f"{sign_id}-{UID}-{ts}-{PHONE_ID}".encode()).hexdigest()
    url = BASE + f"signId={sign_id}&userId={UID}&time={ts}&phoneId={PHONE_ID}&enc={enc}&ctype=stusign"
    r = requests.get(url, headers={"Cookie": COOKIE,
                                   "User-Agent": "ChaoXingStudy/6.7.8 (Android)"}, timeout=10)
    return r.status_code, r.text
```

## 9. 其它签到类型（位置/手势/拍照/蓝牙）落在哪一层 ✅ 已定位

结论：**除「扫码/二维码签到」外，课程签到的其它类型全部在服务端 H5 页面里完成，客户端不参与参数拼装。**

### 9.2 证据：位置/手势/拍照的代码不在客户端
- 全 APK（含 102 个内置 H5 资源）搜 `signType` / `newsign` / `studentSign` / `addsign`：**只在 dex 里命中，内置 H5 一个都没命中**（签到 H5 在 mobilelearn 服务器上）。
- `SignInfoActivity.initView()` 的 View：`sign_course/sign_time/sign_user/sign_tea/sign_fail_msg/bt_again/btnBack` + `sign_success/sign_false/sign_loading` + `ll_course/ll_teacher/tv_message` —— 只有「结果三态 + 重试 + 返回」，**没有任何定位控件、倒计时、相机或手势控件**；全文无 Location/Lat/Lon/Baidu/Gesture 字样。
- 本地定位兜底是死代码：`com.chaoxing.mobile.sign.util.b.a(Context)` 会拼 `"lat:"+lat+"lon"+lon`（GPS/network `getLastKnownLocation`），但 findrefs 显示**无任何外部调用者**；`sign/util/LocationUtils`（百度 SDK、bd09ll、3s 扫描）同样只有包内引用。
- `signType` 在客户端只出现在**教师侧查名单**接口：`com.chaoxing.mobile.s;->G6(int signType, String activeId)` → `https://mobilelearn.chaoxing.com/widget/sign/api/findPuidsByActiveId?signType=%d&activeId=%s`（编号含义由服务端定义）。

### 9.3 蓝牙扫描（beacon）服务的是打卡/座位，不是课程签到
- `com.chaoxing.beacon.BluetoothScanner`（BLE）：`ScanFilter` 按 service data UUID 过滤 —— `00001802-0000-1000-8000-00805f9b34fb`、`0000fff0`、`0000fff1`、`0000fda5`、`0000ab81`、`0000ffe1`、`0000ffd1`；命中后按 MAC/UUID 匹配（`k` 哈希表），结果回调接口 `com.chaoxing.beacon.i`。
- 实现 `com.chaoxing.beacon.i` 的**只有 4 个类**（findrefs impl）：
  1. `com.chaoxing.mobile.webapp.jsprotocal.common.j0$a` —— `j0` 的桥名常量是 **`ClientSeatReserveSignInJsProtocalExecutor`**（图书馆座位预约签到），bridge code 24576/24577/24578，负责申请定位/蓝牙权限；
  2. `Lzp/s$a`；
  3. `com.chaoxing.mobile.office.AddAttendanceBlueToothActivity$a`（office 蓝牙打卡）；

### 10.3 关键安全结论（决定远程可行性）

1. **活体由客户端 SDK 判定**（`CollectResult.liveDetectionStatus` / `SenseLiveResult`），服务端比对的是「本次采集的图 vs 人脸库里已存的 remoteImage」。→ 只要人脸库里有一张本人照片，注入同人照片即可通过比对；活体那一关是纯客户端状态位。
2. **打卡人脸采集不走云盘上传**（`FaceMatchImageUploader.b==2` 时直接返回 status=1），图片只经 base64 进比对请求 → 注入点极少数（`CollectFile.getPath()` 或 base64 变量）。
3. **提交请求带服务端签名**（`sign` + `enc`，enc 由 `vt.n.f(拼接串)` 生成）→ 纯协议重放必须先还原 `vt.n.f`；更省事的是让客户端在无摄像头环境跑完，只在数据层换图。
4. **H5 侧**：全 App 只有 `Lcom/chaoxing/fanya/aphone/view/BaseWebView$b`、`Lj9/d`、`Lyw/a`、`com.fanzhou.refresh.PullToRefreshWebView$b` 等少数 WebChromeClient 子类，其中 **没有一个重写 `onShowFileChooser`**（findrefs method onShowFileChooser 只命中 `com.networkbench.agent.impl.webview.e/f` 两个 APM 包装类）；`Lj9/d.onPermissionRequest` 直接 `super`。→ 拍照/人脸签到若走 `<input type=file capture>`，会落到系统/内核 chooser；若走 `getUserMedia`，权限由默认实现处理。

### 11.3 通道 C 的原理（为什么随便一张截图都能签）

教师端大屏二维码形如：

```
https://mobilelearn.chaoxing.com/widget/sign/e?id=6000059680136&c=251295&enc=0DA06A4208CAAF0961A7EEC658E0EDF5&DB_STRATEGY=PRIMARY_KEY&STRATEGY_PARA=id
```

- `id` = activeId（活动 id，贯穿全程）
- `enc` = 该次签到的**固定票据**（签到开始生成，结束才失效）
- `c` = 每 10 秒递增的**显示用计数器**（防截图转发，服务端提交时不需要它）

客户端扫码后实际发出的请求（抓包实证）：

```
GET https://mobilelearn.chaoxing.com/pptSign/stuSignajax?enc=<enc>&name=<姓名>
    &activeId=<id>&uid=<uid>&clientip=&useragent=&latitude=-1&longitude=-1&fid=<fid>&appType=15
```

→ **只要 cookie 有效 + 一张二维码里的 enc，任何时间任何地点都能签**。响应体是纯文本 `success`。

### 11.4 通道 B（SIGNIN: 前缀）

App 扫码分发器 `com.chaoxing.mobile.main.f.s(String)`：`SIGNIN:` 开头的串被 `com.chaoxing.mobile.s.I7()` 包成

```bash
python3 scripts/autosign.py --uid 12345678 --cookie-file cookies.txt --list-only --want-type --dump

python3 scripts/autosign.py --uid 12345678 --cookie-file cookies.txt --name 张三 --fid 12345

# 定位签到：伪造坐标 + 地址
python3 scripts/autosign.py --uid 12345678 --cookie-file cookies.txt --name 张三     --lat 30.123456 --lon 120.123456 --address "XX大学XX楼"

# 常驻轮询（每 30 秒扫一次，自动只签新活动）
python3 scripts/autosign.py --uid 12345678 --cookie-file cookies.txt --name 张三 --loop --interval 30
```

**唯一签不了的是类型 3（二维码）**——服务端在 `stuSignajax` 里对二维码签到校验 `enc`，而 `enc` 只存在于二维码图片里。这正是通道 A / C 存在的意义：**二维码文本一旦到手，一切都通了**。开源 `xxtSign` 在代码里明确写着"检测到二维码签到，无法自动签到"，也是同一个原因。

### 11.6 弹人脸时怎么过（扫码签到场景）

扫码签到**本身不含人脸**：通道 A 是纯 HTTP，通道 C 是纯 HTTP，通道 B 是网页。人脸只可能出现在两种地方：

1. **H5 页面 JS 桥** —— `com.chaoxing.mobile.webapp.jsprotocal.exam.FaceRecognitionExecutor`
   - `execute(String json)` 由 JS 调用；字段 `funTag`：1 查人脸库 / 2·3 采集 / 4 **比对** / 其它 采集配置
   - 采集完回调 `Y(CollectResult, int, int)` 组装 JSON 回传 JS，含 `LiveDetectionStatus`、`collectStatus`、`signToken`、`cxcid`、`cxtime`
   - **活体是客户端状态位**：`CollectResult.liveDetectionStatus`，`LIVE_STATUS_SUCCESS=1`、`FAIL=0`、`BACK=253`、`UNKNOWN=254`、`SKIP=255`
2. **打卡（office）人脸** —— 走 `/api/apps/punch/user/face/verify/match`，参数含 `facePicture`（base64）+ `sign` + `enc`；服务端拿它和**人脸库里已存的 remoteImage** 比对

**三种过法，按侵入性从低到高**：

| 方案 | 做法 | 适用 |
|---|---|---|
| **S1 协议级绕过（推荐）** | 压根不打开 H5：二维码文本走通道 A/C 直接提交，人脸流程根本不触发 | 扫签类（本用户主场景） |
| **S2 Frida 强制状态位** | hook `CollectResult.setLiveDetectionStatus(1)` + `setImagePath(本人照片)`；已落地 `scripts/frida_face_puppet.js`（`CONFIG.mode=inject`） | H5 页里跳不掉的人脸 |
| **S3 Frida 直接回传 JS 桥结果** | hook `FaceRecognitionExecutor.execute` / `Y(...)`，把伪造 JSON（活体=1、collectStatus=1、signToken 原样）塞回 `q(json)` 回调，让 JS 以为人脸做完了 | 人脸由网页驱动、且比对在服务端 |

**你已把照片传到云端**——那么 S3 是最省事的：云端人脸库里已经有你的图，服务端比对的 `remoteImage` 也是你的图，客户端只要"看起来采集成功"就够了。若人脸流程发起方是原生打卡（`FaceMatchImageUploader.b==2` 那条：图片不上云盘、直接 base64 进比对请求），改 `CollectFile.getPath()` 或 `PunchParams.setFacePictureBase64()` 即可换成云盘任意图。

### 11.7 Cookie 从哪来（无需真机）

三选一，从易到难：

1. **Frida 一键导出**（推荐，模拟器 cx29 已就绪）：
   ```bash
   adb shell "su -c '/data/local/tmp/fsd -D &'"                 # 起 frida-server
   frida -U -f com.chaoxing.mobile -l scripts/frida_sign_hook.js --no-pause
   # java: rpc.exports.dumpcookie()   → 打印当前 Cookie（含 _uid / fid / 各域 token）
   ```
   该脚本同时 hook `SignInfoActivity.m5/j5/r5`、`com.fanzhou.util.j.d`（打印 MD5 原文→enc）、
   `wm.a.a`、`gc.b.j/k`、`volley StringRequest`（打印所有含 sign 的 URL）、`main.f.s`（扫码分发）、
   `FaceRecognitionExecutor.execute/Y`；并提供 RPC `signqr/qrJson`：**直接调 `m5` 完成签到，不用相机、不用对着二维码**。

2. **mitmproxy 抓一次**：模拟器 wifi 代理指向 `<PC_IP>:8080`，装 mitm CA（`-writable-system` 下推到 `/system/etc/security/cacerts`），打开签到页即可看到全部请求头与 cookie。
3. **浏览器 DevTools**：电脑浏览器登录 `mobilelearn.chaoxing.com`，Network → 任意请求 → Copy as cURL，取其中 `-H 'Cookie: …'`。**通道 A/C 只需要这一个域的 cookie**，用这条路最快。

### 11.8 前置条件与失效面

- **必须有登录 cookie**：`_uid`、`fid`、以及 `mobilelearn.chaoxing.com` / `fanyappfy.chaoxing.com` 域的会话票。cookie 静默失效 → 响应变 `{"result":0,"msg":"请重新登录"}`（本机已实测这个形态）。
- **uid = puid**（不是手机号/学号）：`AccountManager.C().D().getPuid()`，脚本 `--uid`。
- **name 用真名**：服务端记录里要匹配名单，URLEncode 后再传。
- **fid**：单位 id，从 cookie 或一次 `loginregister` 响应里拿；填错可能命中 310 用户单位信息错误。
- **限速**：不要对同一 activeId 高频重放（服务端有重复签到判定，重复成功也是 `success` 但会记 `status`），轮询建议 ≥10s。
- **仅通道 A 需要 phoneId**：自造 32 位 hex 即可（服务端只当设备标识，不校验归属）。
- **签名面**：QR 通道的 enc 是**纯 MD5，无服务端 salt**，这是整套协议能被重放的根本原因；office 打卡那条链路的 `vt.n.f()` 签名是另一套（第 10 章已给出 hook 点），不要混用。

### 11.9 待验证项

1. 通道 C 的 `enc` 是否对同一 activeId 在**全部学生间共享**（教师端每班一条二维码 → 大概率共享，一张截图全班可用）；未做多人对比实验。
2. 二维码签到（type 3）在 `stuSignajax` 之外是否还有别的直签端点（`sign/produceSignView` / `widget/sign/api/findPuidsByActiveId` 已列为候选，未验证是否接受 student 身份）。
3. `newsign/studentSign` 提交后服务端是否追加入脸校验（通道 B 的页面 JS 行为未逐行跟踪）。
4. `ifopenAddress(aid)` 的响应字段名（xxtSign 用 `locationText/locationLatitude/longitude`，本 APK 未反编译到该方法）—— 定位签到需要它才能不用手动填地址。

## 12. 进阶：动态（几秒刷新）二维码 + 扫码后人脸校验

> 结论先给：**"几秒刷新"这个特性本身不影响重放**（刷的是显示计数，不是票据），真正决定成败的是「你多久能拿到一次二维码内容」；而**人脸只在 H5 页里，走协议直提交就不触发**。
> 本章所有链路都已在本机跑通（含对线上端点的实测响应），脚本：`qr_sign_remote.py`(v2) / `qr_relay.py` / `userscript/chaoxing_qr_relay.user.js`。

### 12.1 先分清「动态」的三种含义（决定你要不要实时）

| 类型 | 现象 | 变的字段 | 旧截图还能用吗 | 本样本实测 |
|---|---|---|---|---|
| **① 视图计数器型**（大屏/投影最常见） | 大屏二维码每 10 秒显示不同图案 | 只有 `c=251295` 递增 | **能**，`id`/`enc` 全程不变 | 通道 C 形态（`widget/sign/e`），见 §11.3 |
| **② 时间戳型**（原生扫签） | 二维码内容 `{"signId":..,"time":..}` | `time` | 取决于窗口；过期服务端回 **307 二维码时间过期** | 错误码表里确有 307 |
| **③ 真·轮换票据型**（`enc` 每 N 秒换且旧值作废） | 每次扫出的 `enc` 都不同 | `enc` | **不能** | 本样本**未发现**此设计；30 秒可自证（见 12.5） |

**30 秒自证"你的学校属于哪一类"**：同一场签到，隔 20 秒截两张二维码，分别跑

```bash
python3 scripts/qr_sign_remote.py --qr-image shot1.png --dry-run
python3 scripts/qr_sign_remote.py --qr-image shot2.png --dry-run
```

- 两次 `enc`+`activeId` **相同** → ①型，一张截图永久有效（本仓库实测：`c` 变而 `enc` 不变）；
- `time` 不同但 `signId` 相同 → ②型，需要新鲜一点的截图（通常窗口是整个签到时段）；
- 两个都不同 → ③型，必须走 12.2 的自动中继。

**服务端校验顺序（本机线上实测，排错时非常有用）**：

| 端点 | 无 cookie 时的响应 | 说明 |
|---|---|---|
| `fanyappfy.chaoxing.com/usersign/addsign` | `{"statusCode":308,"msg":"signId  not exists"}` | 先查 signId → time → enc → 用户；**未登录不报登录错**，所以可以用假 signId 探活 |
| `mobilelearn.chaoxing.com/pptSign/stuSignajax` | HTTP 200 文本 `请先登录再进行签到` | **先校验登录**，所以这条通道必须有 cookie 才能往下走 |

### 12.2 五档中继：把「看到二维码」到「提交」的延迟压到 1 秒内

| 档 | 做法 | 端到端延迟 | 需要人在场 | 落地物 |
|---|---|---|---|---|
| L1 | 同学截图 → 微信发你 → 手动跑一次 | 10–60 s | 是 | `--qr-image` |
| L2 | 截图自动落进一个同步目录（相册/Syncthing/网盘），脚本盯目录 | 3–15 s | 是 | `--watch DIR` |
| L3 | 脚本自己抓屏解码（adb / macOS screencapture / 目录） | **0.5–1 s** | **否** | `scripts/qr_relay.py` |
| L4 | **在渲染二维码的那台机器上**跑油猴脚本，解出来直接 POST 给你 | <0.5 s | 否 | `userscript/chaoxing_qr_relay.user.js` |
| L5 | 根本不用二维码：直接从 H5 页面/接口拉当前签到参数（含 enc） | — | 否 | 见 12.2.3（待实测） |

#### 12.2.1 L2：目录监听（把"发图"变成"存图"）

```bash
python3 scripts/qr_sign_remote.py --watch ~/qrdrop --uid <puid> --cookie-file ck.txt --interval 1
# 任何设备把二维码截图/文本丢进 ~/qrdrop，脚本 1 秒内解出并签；处理完移到 _done/
```

#### 12.2.2 L3：自动抓屏（推荐，零人工）

```bash
# 抓 AVD / 任何连着 adb 的机器屏幕，解出二维码立刻直签
python3 scripts/qr_relay.py --source adb --serial emulator-5554 --submit \
    --uid <puid> --cookie-file ck.txt --interval 0.7 --stop-on-success

# 抓本机 macOS 屏幕（大屏很近时把电脑摄像头画面/投屏窗口放着）
python3 scripts/qr_relay.py --source screen --submit --uid <puid> --cookie-file ck.txt
```

实测（本机，loop-dir 喂一张大屏二维码）：
```
[+] 第1帧解出（0.16s）: https://mobilelearn.chaoxing.com/widget/sign/e?id=6000059680136&c=251295&enc=0DA06A...
[C] GET https://mobilelearn.chaoxing.com/pptSign/stuSignajax?enc=0DA06A...&activeId=6000059680136&uid=99999&...&appType=15
[C] HTTP 200  请先登录再进行签到          ← 解码→判定→提交 全链路通，只差一条真 cookie
```
配合 `--relay http://127.0.0.1:8765/sign?token=xxx` 还能把「看屏幕的机器」和「持有 cookie 的机器」分开。

#### 12.2.3 L4：在教师电脑上直接看 DOM（二维码本来就是网页）

大屏二维码 = `mobilelearn.chaoxing.com/widget/sign/e?id=..&c=..&enc=..` 这个网页里的 `<canvas>/<img>`。所以在那台电脑上根本不用"截图"：

1. 浏览器装 Tampermonkey → 装 `userscript/chaoxing_qr_relay.user.js`（默认每 500 ms 用 jsQR 解页面上的二维码，内容变了就 POST 到你的中继）；
2. 中继端：
   ```bash
   python3 scripts/qr_sign_remote.py --serve 8765 --uid <puid> --cookie-file ck.txt --token mysecret
   ```
3. 油猴脚本菜单里填 `http://127.0.0.1:8765` + token（跨网段就填运行中继那台机器的内网/VPS 地址 + `--host 0.0.0.0`，**公网务必用 token**）。

**前提是你能碰到那台讲课电脑**（教室 PC 一般就是老师自己的笔记本）。三条常见入口：

```bash
# ① 局域网先看有什么
sudo nmap -sS -p 3389,5900,9222,445,80,8080,5938,8000 -n --open 192.168.1.0/24
# ② 远程桌面：RDP 3389 / VNC 5900（教室 PC 常见未设密码或同用户名密码）
xfreerdp /v:192.168.1.23 /u:teacher /p:'123456' /cert-ignore
# ③ 浏览器远程调试（Chrome 只要带 --remote-debugging-port=9222 就是全权控制）
curl -s http://192.168.1.23:9222/json/list            # 列出所有标签页
curl -s http://192.168.1.23:9222/json/new?about:blank  # 新开标签
#   拿到 webSocketDebuggerUrl 后用 CDP 执行 JS：读取二维码 canvas / 直接把 enc 发出来
```

拿到那台电脑后甚至可以不用中继：油猴脚本里把 `/sign` 的地址直接指向你的公网中继，或者干脆在那边浏览器里 `fetch` 一次提交 URL（`stuSignajax` 只需要 enc/activeId/uid/fid/name，不需要来自学习通客户端的任何东西）。

#### 12.2.4 L5：连二维码都不需要（值得优先验证）

三条线索指向"参数可以从服务端直接拉"：

- `newsign/studentSign?rcode=<整串>&uid=` 打开的是一个 **H5 页面**，页面自己会用 cookie 去拉这次签到的数据（`rcode` 只是入口标记）；
- App 内存在 `widget/sign/api/findPuidsByActiveId?`（那个二维码网页的后端 API）、`pptSign/preSign?activePrimaryId=..`、`ppt/taskAPI/getActiveDataV2?activeId=..`；
- 一旦其中任何一个返回 `enc` 或 `{signId,time}`，那么就**只需要 activeId**（列表接口就能拿到）→ 动态二维码、截图、中继全部作废。

验证方法（需要一个真账号，5 分钟）：
```bash
# 在 AVD 里开一次真实签到页，抓 H5 的所有请求
frida -U -f com.chaoxing.mobile -l scripts/frida_h5_sign_capture.js --no-pause
# 关注输出里带 enc / signId / time / activeId 的 URL 与响应体
```

### 12.3 扫码之后还要人脸，才算签到成功 —— 怎么破

#### 12.3.1 先看人脸到底挂在哪

| 位置 | 类/接口 | 触发条件 | 服务端是否也校验 |
|---|---|---|---|
| H5 页面 JS 桥 | `com.chaoxing.mobile.webapp.jsprotocal.exam.FaceRecognitionExecutor`（funTag 1 查库/2·3 采集/4 比对） | 网页 JS 主动调 `execute(json)` | 比对在服务端：图 vs 人脸库 `remoteImage` |
| office 打卡 | `/api/apps/punch/user/face/verify[/match]`，参数 `facePicture`(base64)+`sign`+`enc` | 打卡人脸 | 是（真比对） |
| **签到本身** | `usersign/addsign`（参数只有 signId/userId/time/phoneId/enc/ctype）<br>`pptSign/stuSignajax`（activeId/uid/fid/name/objectId/address） | — | **两条链路的参数里没有任何人脸字段** |

**所以"扫码后人脸"只存在于 H5 页面这一侧**：学校开的不是「人脸签到类型」（类型表里根本没有这类，只有 普通/拍照/二维码/手势/定位/签到码），而是给 H5 页面加了一道前置人脸流程。→ **只要不走 H5 页面，人脸流程不会被调用。**

#### 12.3.2 四层对策（从 10 秒可验证到最重）

| 层 | 做法 | 成本 | 备注 |
|---|---|---|---|
| **S1 协议直提交**（首选） | 用 `usersign/addsign` / `stuSignajax` 直接交，不打开 H5 | 10 秒 | 若成功 → 人脸问题不存在；本机实测这两条链路的参数结构确实无人脸位 |
| **S2 Frida 伪造人脸结果** | `frida_face_puppet.js`（`CollectResult.setLiveDetectionStatus(1)` + `setImagePath(本人照片)`，LIVE_STATUS_SUCCESS=1）；或 `frida_sign_hook.js` 的 `faceReplyTemplate` 直接把伪造 JSON 回传 JS 桥 | 5 分钟 | 照片已在云端人脸库 → 服务端比对 `remoteImage` 就是你的照片 → **必过**；活体是纯客户端状态位 |
| **S3 重放一次真实人脸提交** | 抓一次你自己（或任何同人）成功的人脸签到请求 → 把 `facePicture`/objectId 换成库里那张图 → 在有效期窗口内重放 | 15 分钟 | 适用于服务端确实校验且 S2 被反制的情况 |
| **S4 相机层喂料** | 媒材预录视频 + 虚拟摄像头（LSPosed VCAM / Camera2 hook），应付眨眼-摇头这类动作活体 | 重 | AVD 的 `-camera-back emulated` 出的是虚拟场景，SDK 会判无脸，必须走 L2 |

判断树：**先 S1**（因为服务端参数结构无人脸位，成功率很高）；S1 被拒（比如返回 `签到失败` 且确定签到本身有成功案例）→ 说明服务端在该活动上附加了校验 → **S2**；S2 也无效 → **S3**。

#### 12.3.3 人脸那一关的关键机制（为什么 S2/S3 能过）

1. **活体是客户端状态位**：`CollectResult.liveDetectionStatus`，`LIVE_STATUS_SUCCESS=1 / FAIL=0 / BACK=253 / UNKNOWN=254 / SKIP=255` —— 没有服务端回执来证明"刚才真的眨眼了"。
2. **比对对象是你上传过的那张照片**：打卡链路的 `FaceMatchImageUploader` 在 `b==2` 时不上云盘、直接 base64 进请求，服务端拿 `remoteImage`（人脸库）比 —— 你既然已经把照片传上去了，**任何一张同为你的照片都能过**。
3. **回传 JS 的 JSON 就是全部证据链**：`currentFaceId / collectStatus / LiveDetectionStatus / recogType / sessionId / SenseDetectionStatus / extraData / signToken / cxcid / cxtime` —— 伪造这一份 JSON 就等于"人脸做完了"。

### 12.4 一键组合（推荐日常用法）

```bash

        --append-log ~/cx_sign.log

# ② 另一边（三选一）：
#   a. 在能看到二维码的机器上加 -relay 自动看屏（L3）
python3 scripts/qr_relay.py --source adb --serial emulator-5554 --relay 'http://127.0.0.1:8765/sign?token=mysecret'
#   b. 在教师电脑浏览器装油猴脚本（L4），其余不用管
```

## 14 伪装层与风控层（v2）

### 14.1 这一层解决什么问题

平台的差异检测不看你"像不像学生"，只看**你的请求和真机不一样的地方**。把差异逐条消掉，比事后解释有用：

| 差异维度 | 真机（学习通 6.7.8） | 裸 requests 脚本 | 后果 |
|---|---|---|---|
| UA | `okhttp/4.12.0` | `python-requests/2.x` | 一眼假 |
| TLS 指纹(JA3) | OkHttp/Conscrypt 密码套件顺序 | Python/OpenSSL 默认 | WAF 直接标 bot |
| 设备参数 | `phoneId`(32hex, SP appProfile/uniqueId)、`schlid`、`device` | 常缺，或每次运行都换 | 同账号指纹漂移 → 关联异常 |
| 头部 | Referer / Cookie / X-Requested-With 齐全 | 常常只有 UA | 行为不连续 |
| 时序 | 人点按钮：秒级抖动，且有前置读接口 | 立刻 POST、等间隔 | 时序特征 |
| 流量构成 | 签到前必有课表/活动列表/详情读 | 只有一条 POST | 孤点请求 |

### 14.2 六维伪装（`scripts/stealth_session.py`）

| # | 维度 | 实现 | 关键值 |
|---|---|---|---|
| 1 | 身份 | `Device` 档案持久化 `~/.chaoxing_device.json`；池内 6 条自洽机型；`phone_id` 32hex 默认**保留不重生成**（通道 A 的 enc 与它绑定） | schema=2；`check_consistency()` 校验 UA/机型/系统/版本自洽 |
| 2 | 指纹 | curl_cffi `impersonate=chrome120` | 缺 curl_cffi 时 `--doctor` 报 WARN |

| 4 | 时序 | 读操作高斯抖动(0.7±0.35s)；写操作最小间隔 8s；拟人延迟 `--delay 3,30` | 无固定秒数、无整点、无突发 |

### 14.3 三层风控

判级表（`RISK_SIGNALS`，18 条语料回归见 `selftest.py` A 组）：

| 级别 | 触发条件 | 处置 | 生命周期 |
|---|---|---|---|
| HALT | 请先登录/未登录/登录已过期/login required、验证码/人机/滑块/SecVerify、账号异常/风控/riskControl/封禁、HTTP 401/403 | **立刻停机**，不再发任何写请求 | 持久化，需人工 `--reset-risk` |
| COOLDOWN | 429 / 操作频繁 / 限流 / too many | 冷却 30 分钟 | 持久化 |
| WARN | 5xx / 系统繁忙 | 单次退避后重试 | 不累计 |
| NOTICE | 业务错误：statusCode 301、306–312、二维码过期、signId not exists | **正常业务分支**：不停机、不计 strikes | 无 |
| OK | `success` / statusCode 300 / 签到成功 | 继续 | 无 |

三层各管一段：

1. **响应层**（`RiskGuard.classify + observe`）：软信号累计 2 次 → 冷却；HALT → 停机并持久化。
2. **闸门层**（`RateGovernor`）：最小间隔 8s、6 次/小时、30 次/24h、静默时段(默认 1–7 点)；冷却中/配额满/静默属**硬阻塞**，直接抛 `RiskCooldown`，绝不把进程挂住。
3. **调用层**（`autosign.py` / `qr_sign_remote.py`）：`RiskHalt` → 打 `[STOP]` + `report()` + 干净返回；`RiskCooldown` → 打 `[WAIT]` + 本轮不重试。

### 14.4 为什么"业务错误"不算风控

最容易自己坑自己的一点：`statusCode=308 (signId not exists)`、`307 二维码过期`、`306 enc 验证错误` 全是**正常业务分支**，算成风控会导致假停机。反过来，`请先登录再进行签到`（通道 C 的真实文案）是真信号 —— 它意味 cookie 失效，此时继续拿旧 cookie 硬试，本身就是"异常登录"特征的来源。

### 14.5 与 everisk / ac_event 的关系（能做什么、不能做什么）

- 客户端 native 风控采集：`assets/RiskStub.dex`（541 类，`com.coralline.sea.*`，梆梆 everisk）+ `libRiskStub.so`；埋点链路 `com.chaoxing.mobile.s.Oa()` → `https://data-xxt.aichaoxing.com/analysis/ac_event?state=&userId=&request_path=&time=&enc=`。
- 这些采集**发生在 App 进程内部**。用脚本直接打接口时它们根本不运行 —— 不是"伪造得不够像"，而是"根本没有"。所以本层的目标只能是**消除行为差异**：让服务端侧的这一次操作，看起来由真人触发。
- 结论：**不要伪造埋点**。`enc` 输入式未逆出，伪造必然对不上；正确做法是让真实行为自然产生埋点（真人登录 App、真实读页面、真实节奏）。

## 15 视频任务点：进度上报协议（enc 逆向 + 回退判定）（2026-11-15 补）

### 15.1 定位与价值

签到之外，学生最费时间的机械操作是**视频任务点**。它的协议比签到更"有状态"，也比签到更能体现"客户端能否安全自动化"：客户端每一格（默认 60 秒）就要主动上报一次进度，**上报节奏、进度、拖拽全都由服务端逐次判定**。

### 15.2 三步链路（全部实证，droidasc + smali 逐指令核对）

| 步骤 | 方法与主机 | 路径 | 代码位置 |
|---|---|---|---|
| 章节卡片 | GET `mooc1-api.chaoxing.com` | `knowledge/cards?clazzid=%s&courseid=%s&knowledgeid=%s&num=%s&isPhone=%d&control=%s&cpi=%s` | `hc.a->W0` / `->Y0` |
| 视频任务 | GET `mooc1-api.chaoxing.com` | `ananas/job?jobid=%s&knowledgeid=%s&courseid=%s&clazzid=%s&jtoken=%s` | `hc.a->q3`（base = `gc.b.d`） |
| 进度上报 | GET `{reportUrl}` | 见 15.3（reportUrl 由服务端下发） | `CourseViewModel->S`（classes6.dex） |

### 15.3 上报串模板与服务端判定

```
?otherInfo=%s&playingTime=%s&duration=%d&akid=null&jobid=%s&clipTime=%s
&clazzId=%s&objectId=%s&userid=%s&isdrag=%d&enc=%s&rt=%s&dtype=Video&view=json
```

响应（gson → `CourseDotRes`）：`result` / `rollbackPoint`（默认 -1）/ `rollbackStatus` / `errorMsg`。

`CoursePlayerFragment->Ua` 的落地行为：

- `result == 1` → 打 `dot_finish_success_`，进度照走；
- `result == 203` → 也打 `dot_finish_success_`，且 `rollbackStatus && rollbackPoint >= 0` 时执行 `this.e.c0(rollbackPoint*1000)` **把播放位置拉回 rollbackPoint 秒**（为 0 时拉 1 ms）；
- `result == 0` → 打 `dot_finish_error_` + 重试容器；
- HTTP 层：非 2xx 一律失败，**HTTP 203 单独当作"成功但可能回退"**（`model.b$n`）。

**这一层就是视频侧的防挂机风控**：它不拒绝你上报，而是用 `rollbackPoint` 把你的进度按回它记录的位置。所以"倍速 + 高频上报"的收益上限由服务端决定，不由客户端决定。

### 15.4 enc（纯本地 MD5，可完全离线复现）

```
plain = "[" + clazzId + "][" + puid + "][" + jobid + "][" + objectId + "]["
      + playing_sec*1000 + "][" + SALT + "][" + duration*1000 + "][" + clipTime + "]"
enc   = md5_hex(plain)
```

三处必须注意：

1. 查询串 `playingTime` 是**秒**，enc 里是**秒 × 1000**；`duration` 同理。
2. 取整方式：先 `ms / 1000` 整除、再 `× 1000`（smali `mul-int/lit16 v5, v5, 1000`）——enc 内的值必是 1000 的整数倍。
3. `clipTime`：`vbegin>=0 且 vend>0` → `"vbegin_vend"`，否则 `"0_<duration>"`；`isdrag=1` 时查询串 `playingTime` 形如 `"起点秒-当前秒"`。

盐是 `CourseViewModel->S` 里夹在两个 `][` 之间的 12 字符常量（含 ! $ _ ~，sha1 前 10 位 `b73e21d9bc`）。脚本默认从本地 smali 自动派生（`--salt-smali` / `--salt-apk` 可现场取）。

### 15.5 其它由服务端下发的开关（决定"能不能加速"）

门禁：`CourseViewModel->j(CourseVideo,String)` —— **reportUrl 非空且播放模式字符串等于 "student"** 才会上报。

## 16 模拟器路线实测：App 在模拟器里能不能跑、能不能替代扫码（2026-11-15 17:4x）

目标：回应"用逆向数据 + 安卓模拟器走 App 自己的扫码链路"。三条判据：① App 在模拟器里能不能跑起来；② 跑起来后是否比 HTTP 直连多出能力；③ 全新安装是否有差别。

### 16.1 结论先给

- App **在模拟器里跑不起来**：启动约 3 秒后**原生自杀**（SIGSEGV 跳向近乎 0 的地址），API 29 与 API 30、去 root 与不去 root、新旧安装**全部一样**。

- 真正能落地的两条：**新鲜帧**（看屏/截图即签，已就绪）与**教师 cookie**（自己取当前二维码内容 + enc，不怕过期）。

## 第 17 章 一键自动签到流水线（教师侧取码 → 学生侧提交）

### 17.1 为什么必须补这一段

1. 学生端页面造不出 enc —— `out/preSign_4000180737792.html` 里 `var aidInEwm = ""; var enc = "";`，enc 只在 `jsBridge.bind('CLIENT_BARCODE_SCANNER', sacn_callback)` 回调中由 `enc = getUrlParam(msg,"enc")` 赋值。

```text
ss.c.b(p3, p4, p5, map):
  map["cxtime"]=p5 ; map["cxcid"]=p3.get()
  keys = sorted(map.keys()); sb = Σ (key + value)
  sb += p4.get()                      # 设备密钥 sc
  return ss.q.b(sb)                   # ss.q.b = MD5(utf8).hex().lower()

qi.c.get() -> mh.a.c().d() -> DeviceInfo.getCid()
qi.g.get() -> mh.a.c().e() -> DeviceInfo.getSc()
  mh.a.b(): clientId = AccountManager.C().D().getClientId()
            DeviceInfo = ne.a.b(com.chaoxing.securitylib.napi.CxDevice.decryptDeviceInfo(clientId), DeviceInfo.class)
```

即 `signToken = md5_hex(「排序后 key+value 串接」+ sc)`，`cxcid = clientId`，二者都是**按账号下发的设备对**（native `CxDevice.decryptDeviceInfo` 解密）。

### 18.6 服务端校验等级（探针实测）

| faceResult | 响应 |
|---|---|
| `{}` | `{"status":0,"code":"CFR001"}` |
| 九字段全伪（无 signToken） | `{"status":0,"code":"CFR007"}` |
| +`extraData` 有、无 signToken | `CFR007` |
| +`extraData`、`signToken=""` | `CFR007` |
| +`extraData`、`signToken="aaaa…"`(32 hex)、`cxcid=deadbeef` | `CFR007` |

→ 服务端在签名/字段一致性层就拒绝，拿不到 `faceEnc`。**纯 HTTP 伪造 faceResult 走不通**：`cxcid/sc` 只存在于安装了 App 的设备里（Web 登录响应不含 clientId，本机 `ck.json` 已验证无该字段；载荷里也没有获取 clientId 的 HTTP 接口）。

## 第 20 章 迟到（status=9）能不能改回「正常签到」——可以（2026-11-16 23:3x–23:4x 实测）

### 20.1 结论速览
- **能改**。迟到、缺勤、早退、请假等一切出勤状态，都由教师侧用同一个接口改写：\`GET /pptSign/updateSignStatus\`。
- **与活动是否结束无关**：活动 status=2（已结束）、甚至 endSign 之后返回 \`签到不存在\` 时，只要签到记录（attendId）还在，状态仍可改。
- **可逆且无损**：迟到(9) ↔ 已签(1) 来回改都返回 \`success\`，记录的 \`attendId\`、\`submittime\`（真实签到时间）不变。
- **学生侧不能改**：客户端没有这个接口；迟到是服务端在入库时写死的状态，再提交也覆盖不了（返回「您已签到过了」）。

### 20.2 迟到是在哪里被判定的
学生页 JS（\`out/preSign_4000180737792.html:349\`）对 \`/pptSign/stuSignajax\` 的响应判定：

| 响应 | 含义 | 客户端提示 |
| --- | --- | --- |
| \`success\` | 按时签到，计入「已签」 | 恭喜你已完成签到 |
| \`success2\` | **已过教师设置的截止时间**（迟到），记录仍入库 | 已过教师设置的截止时间 |

- 位置签到（otherId=4）同样按 \`success2\` 判迟到，与是否带位置参数无关。
