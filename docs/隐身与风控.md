# 隐身与风控：把协议提交伪装成正常签到/正常学习

> 目标不是「骗过某个具体检测」，而是**消除协议客户端与真实 App 之间的可观测差异**，
> 并在被注意到的第一时间停机，避免把「可疑」试成「被处置」。
> 本文所有端点/类名都来自学习通 6.7.8 解壳后的字符串池与 smali，不是推测。

- 伪装层：`scripts/stealth_session.py`（v2）
- 风控层：`scripts/stealth_session.py`（判级/熔断）+ `scripts/risk_guard.py`（CLI/回归）
- 回归测试：`scripts/selftest.py`（43 项，不联网，秒级）

---

## 1. 为什么需要这一层

解壳后可以确认客户端存在**两条独立的旁证链**，纯协议提交天然缺这两条：

| 旁证 | 位置 | 内容 |
|---|---|---|
| 行为埋点 | `com.chaoxing.mobile.s;->Oa(int state, String uid, String requestPath, String time, String enc)` | `GET https://data-xxt.aichaoxing.com/analysis/ac_event?state=%s&userId=%s&request_path=%s&time=%s&enc=%s` |
| 行为埋点（2） | 同类的 `U1(String u,String m,String enc)` | `https://data-xxt.aichaoxing.com/analysis/tab?u=%s&m=%s&enc=%s`；另有 `analysis/datalog?u=%s&s=%s&c=%s&o=%s&st=%d&m=0&d=%d&enc=%s` |
| 风控 SDK | `assets/RiskStub.dex`（541 类，`com.coralline.sea.*` + `com.bangcle.everisk.Agent`） | 梆梆 everisk：设备指纹/环境/行为采集，Application 阶段启动 |

`ac_event` 的语义就是「**App 里发生了什么**」（state + request_path），单独上报到 `data-xxt.aichaoxing.com`（行为分析域，与业务域分开）。这意味着服务端**有能力**把「业务请求」与「客户端自报行为」对账。

> 诚实标注：**服务端是否真的用 ac_event 做签到对账，本轮没有实测证据**。
> 它是「应该消除的差异」，不是「已证实的检测点」。验证实验见 §7。

关键推论：上述采集**发生在 App 进程内部**。用脚本直接打接口时它们根本不运行 —— 不是「伪造得不够像」，而是「根本没有」。所以本层目标只能是消除**行为差异**，而不是编造痕迹。

## 2. 服务端能看到的信号（按可利用度排序）

| # | 信号 | 真实 App 的样子 | 协议客户端的常见破绽 |
|---|---|---|---|
| 1 | Cookie 集 | `mobilelearn`/业务域下的 `JSESSIONID`、`uf`、`_uid`、`_d`、`vc3`、`fid` 等多条 | 只有一两条；跨域 cookie 没带上 |
| 2 | User-Agent | `okhttp/4.12.0`（App 侧）/ WebView 模板含 `schild` `device` | `python-requests/2.x`、`curl/8` |
| 3 | TLS 指纹(JA3) | OkHttp/Conscrypt 或 Chrome/WebView 系 | requests 的固定 ClientHello |
| 4 | 提交时序 | 打开签到页 → 读详情 → 几秒到几十秒后提交 | **0 秒**：一次 HTTP 就命中写接口 |
| 5 | 请求顺序 | 读多写少，写前必读（detail → submit） | 只有写接口，从不读页面 |
| 6 | `clientip` / `useragent` 参数 | **客户端本身就传空**（`stuSignajax?...&clientip=&useragent=&...`） | 自作聪明填真 IP/UA，反而不像客户端 |
| 7 | 设备指纹一致性 | 同一 uid ↔ 同一 phoneId/机型/UA | 每次运行换 phoneId；多 uid 共用一个 phoneId |
| 8 | 地理与时间 | 定位坐标与历史轨迹连续；提交时间在活动窗口内 | 跨城市瞬移、坐标 `-1`、活动刚发布就秒交 |
| 9 | 频率/并发 | 一个人不可能同时交 5 个班的签到 | 多账号同 IP 同秒并发 |
| 10 | `isdrag` / 播放心跳 | playingTime 单调、步长≈心跳间隔 | 直接汇报满进度、isdrag=1 |

## 3. 六维伪装（`scripts/stealth_session.py` v2）

| # | 维度 | 实现 | 关键值/证据 |
|---|---|---|---|
| 1 | 身份 | 设备档案持久化 `~/.chaoxing_device.json`（schema=2）；池内 6 条自洽机型（Xiaomi 2201122C/A12、SM-S9180/A13、PGT-AN10/A13、PGT110/A14、V2227A/A13、ELS-AN00/A12）；`phone_id` 32hex **默认保留不重生成** | 通道 A 的 `enc = md5(signId-uid-time-phoneId)` 与 phoneId 绑定，换了 enc 就变 |
| 2 | 指纹 | 装了 `curl_cffi` 时 `impersonate="chrome120"` | `--doctor` 第 2 项；缺库则 WARN |
| 3 | 头部 | `base_headers()`：UA + Accept + Accept-Language + X-Requested-With + Referer；H5 路径自动切 WebView UA 模板 | UA 与样本字符串一致：`okhttp/4.12.0` |
| 4 | 时序 | 读操作高斯抖动（0.7±0.35s）；写操作最小间隔 8s；`--delay 3,30` | `--simulate` 干跑时序表：无固定秒数、无整点、无突发 |
| 5 | 流量 | 写操作前自动跑 1–2 条只读学习动线 `COVER_FLOW` | 4 条：`mycourse/backclazzdata`、`ppt/activeAPI/courseactivelist`、`teachingPlanAPI/noFinishActiveCount`、`ppt/activeAPI/personalActiveLibraryV2` |
| 6 | 审计 | `~/.chaoxing_audit.jsonl` 脱敏记录：时间/uid 尾 6/方法/URL(打码)/码/字节/耗时/判级/TLS 模式/UA 模式 | 长值打码 `abc***`，仅保留 uid、activeId、courseId 等参数值 |

一致性校验 `Device.check_consistency()`：phoneId 必须 32hex / UA 必须是 `okhttp/` / WebView UA 里的 Android 版本与档案一致 / build 串存在 / 机型在池内。**档案漂移比没有档案更可疑。**

## 4. 三层风控

### 4.1 判级表（`RISK_SIGNALS`）

| 级别 | 触发条件 | 处置 | 生命周期 |
|---|---|---|---|
| HALT | 请先登录 / 未登录 / 登录已过期 / login required；验证码 / captcha / 人机 / 滑块 / SecVerify；账号异常 / 风险 / riskControl / 封禁 / 冻结；HTTP 401、403 | **立刻停机**，不再发任何写请求，并提示「去 App 人工登录一次」 | 持久化，需 `--reset-risk` |
| COOLDOWN | 429 / 操作频繁 / 限流 / too many | 冷却 30 分钟 | 持久化 |
| WARN | 5xx / 系统繁忙 | 单次退避后重试 | 不累计 |
| NOTICE | **业务错误**：statusCode 301、306–312；二维码过期；signId not exists | 正常业务分支：不停机、不计 strikes | 无 |
| OK | `success` / statusCode 300 / 签到成功 | 继续 | 无 |

最容易被自己坑的地方：`308 signId not exists`、`307 二维码过期`、`306 enc 验证错误` 都是**正常业务分支**，算成风控会造成假停机。反过来 `请先登录再进行签到`（通道 C 的真实文案）是真信号：cookie 失效后继续拿旧 cookie 硬试，本身就是「异常登录」特征的来源。

### 4.2 三层分工

1. **响应层** `RiskGuard.classify()/observe()`：软信号累计 2 次 → 冷却；HALT → 停机并持久化到 `~/.chaoxing_risk.json`。
2. **闸门层** `RateGovernor`：最小间隔 8s、6 次/小时、30 次/24h、静默时段（默认 1–7 点不做写）。冷却中/配额满/静默属**硬阻塞** → 直接抛 `RiskCooldown`，**不把进程挂住**（`max_sleep=90s`）。状态持久化在 `~/.chaoxing_rate.json`。
3. **调用层**（`autosign.py` / `qr_sign_remote.py`）：`RiskHalt` → 打 `[STOP]` + `report()` + 干净返回（不重试）；`RiskCooldown` → 打 `[WAIT]` + 本轮不重试。

```bash
python3 scripts/autosign.py --uid <puid> --cookie-file cookies.txt --name <姓名> --stealth --max-writes-per-hour 4 --min-interval 12 --quiet-hours 1-7
python3 scripts/qr_sign_remote.py --qr-image shot.png --uid <puid> --cookie-file cookies.txt --stealth
```

`--quiet-hours none` 关闭静默时段（不建议）；`--quiet-hours 22-6` 支持跨零点。

## 5. 反模式清单（这些比「没伪装」更可疑）

1. **0 秒提交**：扫码后立刻打写接口。二维码签到本身要快，但也得有「打开页面→点按」的时间量级。
2. **只写不读**：会话里第一个请求就是 `stuSignajax`。
3. **phoneId 漂移**：每次运行随机新 phoneId，或一个 phoneId 配多个 uid。
4. **填 `clientip`/`useragent`**：客户端传空，填了就是唯一的那个。
5. **多账号同 IP 并发**：代理池要按账号隔离出口 IP。
6. **坐标**：定位签到给 `-1,-1`，或给一个与上次相隔千里的点。
7. **活动刚发布就交**：`courseactivelist` 返回后立刻提交；`--interval` 不要小于 20–30s。
8. **isdrag=1 / 满进度视频**：见 `docs/学生高频操作接口.md` §2。
9. **凌晨自动签**：挂机整晚反而是最强的异常特征（默认静默时段就是为了挡住这种行为，不是为了「藏起来偷偷签」）。

## 6. 学习流量掩护（「隐藏成正常学习」）

按「正常学生的一天」编排：

```
打开课程列表 → 看未完成任务点 → 打开消息(noFinishActiveCount)
  → 看到活动 → 拉详情(signDetail) → [拟人延迟] → 提交签到
  → 之后随手读两条课程/成绩接口
```

即：**写操作永远夹在成串的读操作中间**，且每次会话的接口序列不完全相同（`cover_traffic` 内部随机 sleep 1.5–5s；`warmup()` 全跑）。意义在于：如果服务端真拿 `ac_event` 对账，它看到的是「一个学生在看课程/消息」，而不是「一个脚本在打写接口」。

## 7. 怎么验证有没有被风控（A/B 实验设计）

1. **基准样本**：真机 + `scripts/frida_sign_hook.js`（能 dump volley StringRequest、okhttp Headers、CookieManager）抓一次真实签到，保存：完整头、Cookie 集、请求顺序、时间戳、参数。
2. **A 组**：`--stealth --no-tls`（requests 指纹）；**B 组**：`--stealth`（curl_cffi 指纹）。同账号、同活动类型、隔天各跑一次。
3. 观察指标：回包差异（`success` vs 其它）、迟到失败（提交当时成功、10 分钟后变成异常）、同课程其他同学是否出现「签到异常」。
4. 若 A/B 无差异 → 当前检测强度低；若 B 明显更好 → 存在 TLS/头层面的判据。
5. 反面证据优先：**能证明「没有任何差异被利用」比「看起来没被抓」更有价值**。没有实测就写「未验证」。

## 8. 明确不做的事

- **不伪造 `ac_event`/`datalog` 埋点**。原因：`enc` 的 md5 输入式还没逆出来（只确认了 frame 构造点 `s->Oa`），且伪造埋点等于主动制造不一致——真客户端上报的是它自己做的事，脚本没有「那一帧」。正确做法是让真实行为自然产生埋点（§6 的编排）。
- **不绕设备指纹校验**：`RiskStub` 只做采集，本 App 侧未发现「采集不过就不让签」的分支（签到链路里没有它的调用）。
- **不在凌晨自动签**、不在配额用尽后硬试。

## 11. 踩过的坑（留档）

1. `wait_for_slot()` 会为一次 30 分钟冷却睡满 → CLI 看起来像卡死。现在：冷却/配额/静默属硬阻塞，超过 `max_sleep=90s` 直接抛 `RiskCooldown`。
2. `parse_quiet` 当初没导出 → 调用方 import 失败后**静默回退到降级实现**（「能跑」，但伪装层没生效）。`selftest.py` 现在断言 `RiskHalt.__module__ == "stealth_session"`，防止再次静默降级。
3. 去重是 per-`Signer` 的：两个实例之间不会自动去重。
4. 文档里写含反引号/反斜杠的代码片段后，必须 grep 校验转义残留。

---

## 12. 边界（说清楚）

- 本层保证「**不比真人更可疑**」，不保证「高频不被抓」。单账号的安全上限是真人节奏，不是技术上限。
- 静默时段默认 (1,7)，是**限制**而不是「隐身衣」：它挡住的是最容易暴露的挂机行为。
- 未实测：`ac_event` 是否被服务端用于签到对账；`enc` 输入式未逆出。
