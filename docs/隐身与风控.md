# 隐身与风控：把协议提交伪装成正常签到/正常学习

> 目标不是「骗过某个具体检测」，而是**消除协议客户端与真实 App 之间的可观测差异**。
> 本文所有端点/类名都来自 6.7.8 解壳后的字符串池与 smali，不是推测。

## 1. 为什么需要这一层

解壳后可以确认客户端存在**两条独立的旁证链**，纯协议提交天然缺这两条：

| 旁证 | 位置 | 内容 |
|---|---|---|
| 行为埋点 | `com.chaoxing.mobile.s;->Oa(int state, String uid, String requestPath, String time, String enc)` | `GET https://data-xxt.aichaoxing.com/analysis/ac_event?state=%s&userId=%s&request_path=%s&time=%s&enc=%s` |
| 行为埋点（2） | 同类的 `U1(String u,String m,String enc)` | `https://data-xxt.aichaoxing.com/analysis/tab?u=%s&m=%s&enc=%s`；另有 `analysis/datalog?u=%s&s=%s&c=%s&o=%s&st=%d&m=0&d=%d&enc=%s` |
| 风控 SDK | `assets/RiskStub.dex`（541 类，`com.coralline.sea.*` + `com.bangcle.everisk.Agent`） | 梆梆 everisk：设备指纹/环境/行为采集，Application 阶段启动 |

`ac_event` 的语义就是「**App 里发生了什么**」（state + request_path），单独上报到 `data-xxt.aichaoxing.com`（行为分析域，与业务域分开）。这意味着服务端**有能力**把「业务请求」与「客户端自报行为」对账。

> 诚实标注：**服务端是否真的用 ac_event 做签到对账，本轮没有实测证据**。
> 它是"应该消除的差异"，不是"已证实的检测点"。验证实验见 §6。

## 2. 服务端能看到的信号（按可利用度排序）

| # | 信号 | 真实 App 的样子 | 协议客户端的常见破绽 |
|---|---|---|---|
| 1 | Cookie 集 | `mobilelearn`/业务域下的 `JSESSIONID`、`uf`、`_uid`、`_d`、`vc3`、`fid` 等多条 | 只有一两条；跨域 cookie 没带上 |
| 2 | User-Agent | `... com.chaoxing.mobile/ChaoXingStudy_10946`（含 `schild`/`device`） | `python-requests/2.x`、`curl/8` |
| 3 | TLS 指纹(JA3) | Chrome/WebView 系 | requests 的固定 ClientHello |
| 4 | 提交时序 | 打开签到页 → 读详情 → 几秒到几十秒后提交 | **0 秒**：一次 HTTP 就命中写接口 |
| 5 | 请求顺序 | 读多写少，写前必读（detail → submit） | 只有写接口，从不读页面 |
| 6 | `clientip` / `useragent` 参数 | **客户端本身就传空**（`stuSignajax?...&clientip=&useragent=&...`） | 自作聪明填真 IP/UA，反而不像客户端 |
| 7 | 设备指纹一致性 | 同一 uid ↔ 同一 phoneId/机型/UA | 每次运行换 phoneId；多 uid 共用一个 phoneId |
| 8 | 地理与时间 | 定位坐标与历史轨迹连续；提交时间在活动窗口内 | 跨城市瞬移、坐标 `-1`、活动刚发布就秒交 |
| 9 | 频率/并发 | 一个人不可能同时交 5 个班的签到 | 多账号同 IP 同秒并发 |
| 10 | `isdrag` / 播放心跳 | playingTime 单调、步长≈心跳间隔 | 直接汇报满进度、isdrag=1 |

## 3. 已实现的伪装层：`scripts/stealth_session.py`

```bash
python3 scripts/stealth_session.py --show          # 看当前设备档案（uid/phoneId/UA）
python3 scripts/stealth_session.py --new-device    # 重新生成档案（换机器才需要）
python3 scripts/stealth_session.py --probe https://mobilelearn.chaoxing.com/
python3 scripts/stealth_session.py --warmup        # 掩护流量自测
```

它提供四件事：

1. **设备档案持久化** `~/.chaoxing_device.json`：uid ↔ phoneId ↔ 机型 ↔ UA 一次绑定，反复运行指纹不变。
   - phoneId 同时是通道 A（`fanyappfy/usersign/addsign`）`enc` 的输入，档案统一后 enc 与头里的 device 串才自洽。
2. **完整头**：UA（`ChaoXingStudy_10946`）、`Accept-Language: zh-CN`、`Connection: keep-alive`、`Referer: https://mobilelearn.chaoxing.com/`，可选 `X-Requested-With: com.chaoxing.mobile`。
3. **TLS 指纹**：装了 `curl_cffi` 时用 `impersonate="chrome120"`，JA3 与 Chrome 一致（本机实测已生效：`TLS 指纹: curl_cffi(chrome)`）。
4. **拟人延迟 + 掩护流量**：`human_delay(3,30)`；`warmup()` 在提交前先打 4 条只读接口（实测全部 200）：
   ```
   mooc1-api.../mycourse/backclazzdata?view=json&rss=1
   mobilelearn.../ppt/activeAPI/courseactivelist?status=1&page=1&pageSize=20
   mobilelearn.../teachingPlanAPI/noFinishActiveCount?chatId=&tuid=<uid>
   mobilelearn.../ppt/activeAPI/personalActiveLibraryV2?page=1&pageSize=20
   ```

接到现有脚本上（已改好）：

```bash
python3 scripts/autosign.py --uid <puid> --cookie-file cookies.txt --name <姓名> --fid <fid> --stealth
python3 scripts/qr_sign_remote.py --qr-image shot.png --uid <puid> --cookie-file cookies.txt --stealth
```

`--stealth` 做的事：设备档案 → 完整头 + TLS 指纹 → 掩护流量 → 提交前 3~30s 随机延迟。
`--delay 0,0` 可关延迟；`--no-tls` 关 TLS 指纹（用于 A/B 对比实验）。

## 4. 反模式清单（这些比"没伪装"更可疑）

1. **0 秒提交**：扫码后立刻打写接口。二维码签到本身就是要快，但也要 ≥ 打开页面到点按的时间量级。
2. **只写不读**：会话里第一个请求就是 `stuSignajax`。
3. **phoneId 漂移**：每次运行随机新 phoneId，或一个 phoneId 配多个 uid。
4. **填 `clientip`/`useragent`**：客户端传空，你填了就是唯一的那个。
5. **多账号同 IP 并发**：代理池要按账号隔离出口 IP。
6. **坐标**：定位签到给 `-1,-1` 或者给一个和上一次相隔千里的坐标；正确做法是给教室附近、且与历史一致的点。
7. **活动刚发布就交**：`courseactivelist` 返回后立刻提交，比真人快太多；`--interval` 不要小于 20~30s。
8. **isdrag=1 / 满进度视频**：见 `docs/学生高频操作接口.md` §2。

## 5. 学习流量掩护（"隐藏成正常学习"）

除了 `warmup()` 那 4 条只读，还可以按「正常学生的一天」编排：

```
打开课程列表 → 看未完成任务点(gas/course) → 打开消息(noFinishActiveCount)
  → 看到活动 → 拉详情(signDetail) → [拟人延迟] → 提交签到
  → 之后随手读两条课程/成绩接口
```

即：**写操作永远夹在成串的读操作中间**，且每次会话的接口序列不完全相同（`warmup` 内部本来就随机 sleep 1.5–4s）。
这套编排的意义是让 `ac_event`（如果服务端真在对账）看到的是"一个学生在看课程/消息"，而不是"一个脚本在打写接口"。

## 6. 怎么验证有没有被风控（A/B 实验设计）

1. **基准样本**：真机 + `scripts/frida_sign_hook.js`（已能 dump volley StringRequest、okhttp Headers、CookieManager）抓一次真实签到，保存：完整头、Cookie 集、请求顺序、时间戳、参数。
2. **A 组**：`--stealth --no-tls`（默认 requests 指纹）；**B 组**：`--stealth`（curl_cffi 指纹）。同账号、同活动类型、隔天各跑一次。
3. 观察指标：回包差异（`success` vs 其它）、迟到失败（提交当时成功、10 分钟后变成异常）、同课程其他同学是否也被标记（生成"签到异常"表）。
4. 若 A/B 无差异 → 当前检测强度低，协议客户端够用；若 B 明显更好 → 说明存在 TLS/头层面的判据。
5. 反面证据优先：**能证明"没有任何差异被利用"比"看起来没被抓"更有价值**。没有实测就写"未验证"。

## 7. 明确不做的事

- 不伪造 `ac_event`/`datalog` 埋点。原因：`enc` 的 md5 输入式还没逆出来（只确认了 frame 构造点 `s->Oa`），
  且**伪造埋点等于主动制造不一致**——真客户端上报的是它自己做的事，脚本没有"那一帧"。
  正确做法是让**真实行为**自然产生埋点（§5 的编排），而不是编造事件。
- 不绕设备指纹校验：`RiskStub` 只做采集，本 App 侧未发现"采集不过就不让签"的分支（签到链路里没有它的调用）。
