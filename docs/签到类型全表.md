# 不同课程的「不同签到方式」全表

关键认知：**签到类型是服务端数据，不是客户端代码**。每门课一次签到在服务端就是一个 *活动(active)*，
它的类型由两个字段决定（`GET /newsign/signDetail?activePrimaryId=<aid>&type=1` 的响应）：

```
otherId == 0 && ifPhoto == 1  -> 1 拍照签到
otherId == 0 && ifPhoto != 1  -> 2 普通签到
otherId == 2                  -> 3 二维码签到
otherId == 3                  -> 6 手势签到
otherId == 4                  -> 5 定位签到
otherId == 5                  -> 7 签到码
其它                          -> 0 未知
```

客户端只负责"渲染哪种 UI"，**提交都落到同两个端点**（`stuSignajax` / `usersign/addsign`），
所以类型差异只体现在**几个附带字段**上 —— 这就是本表存在的意义。

## 1. 各类型对照表

| 类型 | 大类 | 需要额外信息 | 提交参数（在通用参数之外） | 能否纯协议直签 | 本客户端证据 |
|---|---|---|---|---|---|
| **2 普通签到** | 无门槛 | 无 | 无 | ✅ 完全可 | 通道 C/D，`autosign.py --want-type 2` |
| **1 拍照签到** | 需要图片 | 一张图先上传换 `objectId` | `&objectId=<oid>` | ⚠️ 需先走上传接口拿 objectId | 类型判定 + 参数位已确认，上传接口未挖（见 §3 待办） |
| **3 二维码签到** | 需要二维码 | 二维码里的 `enc` 或 `{signId,time}` | C 通道：`&enc=<enc>`；A 通道：`&signId=&time=&enc=<本地MD5>` | ✅ 有二维码即可 | 通道 A/C，`qr_sign_remote.py` |
| **5 定位签到** | 需要位置 | 经纬度；若老师开了"详细地址"还要 `address` | `&latitude=<lat>&longitude=<lon>`（+ `&address=<文本>`），**并且必须带隐藏参数 `ifTiJiao=1`** | ✅ 可（位置可任意伪造，`-1,-1` 也行） | `autosign.py --lat --lon --address` |
| **6 手势签到** | 需要手势 | 老师给的手势顺序 | 老接口的 `scrawl`/手势字段 | ❓ 本客户端已无手势代码（详见 §2） | 载荷内 "手势" 命中 0 |
| **7 签到码** | 需要口头码 | 老师口头报的 4–6 位数字 | 参数名未在客户端出现（H5 侧） | ❓ 需一次真活动抓包确认字段名 | 客户端字符串池无 `signCode` 类字段 |
| **0 未知** | — | — | 先按普通签到试 | — | — |

## 2. 为什么"手势签到"在本客户端消失

解壳后的 388,486 条字符串里 **"手势" 命中 0**；`SignInfoActivity` 只有扫码一条路径，
H5 侧 `assets/schedule/*`（课表页）无签到逻辑。结论：**本版本客户端不再本地实现手势签到**，
若学校仍开此类活动，只会以 H5 形式出现 → 走通道 B 或让老师侧接口兜底。
反之，服务端 `signDetail` 仍会返回 `otherId==3`，所以判定表要保留。

## 3. 两条客户端路径与类型的关系

| | 原生路径 | H5 路径 |
|---|---|---|
| 触发 | 服务端下发"签到"资源 → `resource.p.k()` 开 `SignInfoActivity` | 二维码以 `SIGNIN:` 开头 → `newsign/studentSign?rcode=` 打开网页 |
| 支持类型 | 只处理 `{time,signId}` 二维码 | 服务端页面按类型渲染（普通/定位/签到码/手势…） |
| 有相机吗 | 有（只用于扫二维码） | 无 |
| 有扫脸吗 | **无**（该 Activity 不引用任何人脸类） | 可能（JS 桥 `FaceRecognitionExecutor`） |
| 自动化建议 | 通道 A/C/D 直提，不走 UI | 能不出现在这条路径就避开（人脸只挂这里） |

## 4. 一次签到的完整判定流程（可直接照做）

```bash
# ① 我是哪些班的学生
curl 'https://mooc1-api.chaoxing.com/mycourse/backclazzdata?view=json&rss=1'   # roletype==3 才是学生班
#    拿出 classId / courseId / cpi

# ② 这个班正在进行什么活动
curl 'https://mobilelearn.chaoxing.com/ppt/activeAPI/taskactivelist?courseId=<cid>&classId=<clid>&uid=<uid>&cpi=<cpi>'
#    返回 {"result":1,"activeList":[{"id":<activeId>,"status":1,...}]}   status==1 进行中

# ③ 这次签到是什么类型
curl 'https://mobilelearn.chaoxing.com/newsign/signDetail?activePrimaryId=<aid>&type=1'
#    用 §1 的表判定 otherId/ifPhoto

# ④ 按类型提交（见 §1 的"额外参数"列）
#    普通/定位/签到码：pptSign/stuSignajax?activeId=<aid>&uid=<uid>&...&appType=15&fid=0&name=<姓名>
#    二维码：先拿 enc，再 stuSignajax（或走 usersign/addsign 的通道 A）
#    成功判定：响应纯文本 == "success"
```

## 5. 待实测（本表里标 ❓ 的两行）

1. **签到码（7）的字段名**：一次真实"签到码"活动抓包，看 H5 提交里那个 4–6 位数字叫什么（`signCode`/`code`/`answer`）。
2. **拍照（1）的 `objectId` 从哪来**：抓一次真实拍照签到，看上传接口路径与返回结构（大概率在 `mobilelearn` 或 `fanyappfy` 域的 `upload` 类接口）。
3. **手势（6）是否还能用老接口提交**：需要一次真手势活动对照。
