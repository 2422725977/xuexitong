# 拍照签到（ifPhoto=1）专项：为什么纯 HTTP 打不通

记录时间：2026-11-16 23:00 – 2026-11-17 02:00｜样本：学习通 Android 6.7.8（package com.chaoxing.mobile，梆梆 SecNeo 加固）

---

## 0. 结论速览

1. 拍照**不是**独立签到类型。教师侧 otherId=1 会被服务端直接拒（{"status":-1,"errormsg":"不支持的签到类型"}）；正确形态是 otherId=0 + 表单修饰位 ifPhoto=1（教师页复选框 id=ifPhoto）。signDetail 里的 ifPhoto 只是回读该修饰位。
2. **提交请求不是 App 原生代码发出的**，而是 WebView 里 H5 页面的 JS 打到 /pptSign/stuSignajax。App 只贡献四样：UA 头、cookie、deviceCode、objectId。
3. 服务端对 ifPhoto 活动的判定是**活动级 + 请求级凭证**，与参数形状无关：
   - 不带 objectId、不带 photoResult → photoAuthError_PCR007
   - 不带 cookie → 仍 PCR007（而普通活动同条件回的是「请先登录再进行签到」）
   - 教师身份、有学校单位的账号提交 → 仍 PCR007
   - 普通活动带全套拍照参数 → 「您已签到过了」（多余参数无害）
   - 伪造 activeId → tengine 500（服务端会先解析活动）
4. 结论：缺的不是客户端参数，而是服务端为「会话 / 设备 / 账号」记的状态。已排除：UA、fid、name、deviceCode、photoResult 形状、preSign 上下文（含 ext）、行为分析回传、ifTiJiao、GET/POST、上传通道、图片随机化。

## 1. 上传链：objectId 从哪来（纯 Python 可复现）

    GET  https://pan-yz.chaoxing.com/api/token/uservalid        -> JSON 里的 _token（必须单独取字段，不能整串当 token）
    POST https://pan-yz.chaoxing.com/upload?_from=mobilelearn&_token=<token>
         multipart：file=<图片，建议带文件名> + puid=<账号 puid>
    响应示例：
    {"result":true,"msg":"success","crc":"...","objectId":"<32hex>",
     "resid":1329264001597685760,"puid":[学生PUID],
     "data":{"disableOpt":false,"resid":...,"encryptedId":"<逐次不同的令牌>"}}

- 必须带 `_from=mobilelearn` 与 `_token`，否则被 IP 白名单拒：{"result":false,"msg":"您的ip：x.x.x.x 不被允许访问"}
- objectId 是**内容寻址**：同一张图无论走哪条通道、带不带 fid/activeId/type，objectId 恒等；每次变化的只有 resid 与 data.encryptedId
- 备用云盘通道：POST https://pan-yz.cldisk.com/upload（同内容寻址）
- 另有 (a) 老接口 /upload/uploadfile 只回 resid；(b) 从云盘根目录列表反查 objectId（pan-yz 首页抓 enc/_rootdir → /opt/listres）
- 上传成功 ≠ 提交成功：我们上传 10+ 次全部拿到 objectId，提交仍 PCR007

## 3. deviceCode 客户端公式（反汇编还原）

- 桥映射：ProtocolTable_Impl 里 "CLIENT_DEVICE_FLAG" → 类 Lxp/b
- 取值：先取设备 OAID（Lls/h;->j()->l()），空则 UMConfigure.getOaid(Context, listener)；uniqueId 为空或不匹配 ^(0{16,64})$ 时回退静态值 Lan/b;->d()
- 加密：16 字节常量密钥 + AES/ECB/PKCS5Padding + Base64.NO_WRAP

    deviceCode = Base64_no_wrap( AES_ECB_PKCS5( uniqueId ) )

- 另有 "CLIENT_DEVICE_ID" 桥（jsprotocal/common/p0）返回 {"uuid": <静态设备 uuid>}，与 deviceCode 是两个不同标识；H5 拍照页只用 CLIENT_DEVICE_FLAG
- 上游两个可用实现直接**随机生成** deviceCode（SHA-256(uuid1+uuid2) → Base64，88 字符）也能正常签到 → 说明 deviceCode 不是 PCR007 的闸门

三个最说明问题的反例：

## 6. 服务端行为空间与端点否证

- 客户端 dex 里**没有任何拍照授权端点**；全库唯一 upload URL 是 photo.chaoxing.com/banner/uploadApi.do（个人头像上传）。
- 12 条候选端点（pptSign/uploadPhoto、pptSign/photoAuth、pptSign/photoTask、newsign/uploadPhoto、v2/apis/sign/photoAuth …）全部 tengine 500（路径不存在）。
- /v2/apis/sign/refreshQRCode 对位置/拍照类活动回 {"result":0,"errorMsg":"非二维码签到"}。
- signDetail 里 ifPhoto 只是回读位；content / configJson 中没有拍照字段；pptActiveInfo 的关键字段：openCheckFaceFlag=0、ifopenAddress、ifphoto、ifrefreshewm、locationRange、isbegins。
- 教师页「发起签到」表单提交体 60+ 字段与我们 newTaskSign 调用等价，无遗漏字段；picId / planId 为静态空值。
- 教师活动页 /widget/active/teaActiveView 在实验时段恒 500（此前可用）→ 取活动 content 改用 signDetail + preSign 页。

## 7. 未闭合点：三种候选解释

1. **请求会话与设备注册绑定**：我们的两个 cookie 都来自网页登录（学生账号 fid=0 且 unitConfigInfos=[]，没有任何学校单位；教师账号 fid=1022 也不行）→ 服务端可能要求「设备已注册 / 会话已与设备绑定」。
2. **活动来源**：我们的活动是调 /pptSign/newTaskSign 创建的（signDetail 显示 isClone=1、parentId=aid-1），可能需要新版活动库或群聊路径创建的活动。
3. **objectId 来源**：服务端可能只认「App 原生上传会话」产出的 objectId（HTML5 页面的 cloudupload 走 CloudUploadConfig，URL 与业务参数由服务端 mirror 配置下发；dex 内无硬编码）。
